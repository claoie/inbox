# §F.cross-cutting — Always load

Applies to every diff regardless of code area — code hygiene, PII, verification discipline, scale principles, testing gotchas that reach across the codebase.

- **Replacing raw interpolation with a function call turns every loose-typed field into a crash site** — `` `x: ${v}` `` stringifies `undefined` harmlessly; `f(v)` where `f` does `v.replace(...)` throws and takes the whole request with it. Flag HIGH when a hardening diff wraps a field whose **runtime** nullability is looser than its TypeScript type — the giveaway in this codebase is data read straight off a JSONB column with no model hydration (`store.ts` casts `model.attachments as AttachmentType[]` with no `new Attachment(...)`, so `contentType`/`filename` genuinely arrive `undefined` on old rows). inbox #828 R1 med 2. Require the same fallback the sibling formatter already uses (`formatBodyStructure`'s `application/octet-stream` / `unnamed`), so two surfaces describing one object can't disagree — and require a test with the field absent, not just hostile.
- **Whole-file reformat churn in a scoped PR (prettier)** — flag any diff where files carry large reflow-only hunks unrelated to the PR's stated scope, especially alongside a lockfile change. The repo does not declare prettier or wire it into a script, lint, CI or the Dockerfile; it tracks a `.prettierrc.json` that sets no `printWidth`, so running it still falls back to the **80-column default** and reflows every touched file. `eslint` is the only formatter of record; de-facto width is ~100. Direct hit on the scope rule (§B).
- **Don't rebuild a Set from a Map's keys** — `Map<string, X>` already supports `.has(id): boolean`. If a diff materializes `const set = new Set(); map.forEach((_, k) => set.add(k));` only to call `set.has(id)`, that's redundant. Use the Map directly. Function params that take a "do you have this id" lookup should be typed `ReadonlyMap<string, V>` if the value type is meaningful, or structurally `{ has(id: string): boolean }` if it isn't — both make Set OR Map work without a parallel build.
- **Cache-busting import specifier as a mock escape hatch** — Bun keys the module registry by full specifier string, so `await import(`${import.meta.dir}/x.ts?real=N`)` reaches the REAL module even when something mock.module'd `./x`. Legitimate and sometimes the only way to test a function a barrel mock has stubbed graph-wide (inbox #775, 2026-08-04). But flag two failure modes: (a) cache-busting a module with a **large transitive graph** instantiates a second copy of that whole graph — doing it to `smtp.ts` broke 46 unrelated tests; it is safe only for leaf-ish modules; (b) it usually has to be paired with a **leaf `client`-module pool mock** (the "first importer of `client.ts` wins" hazard), and that mock must be scoped inside the single test and restored, never registered at load time — a load-time one is process-global and broke the same 46 tests. Prefer adding the case to the existing test file that already has the harness; check whether the suite already supplies the positive control before building any of this.
- **A barrel stub with an explicit export list goes stale silently** — `smtp.test.ts` mock.modules `"server"` listing only the symbols it needs. When a diff adds a NEW barrel import to the source file (e.g. `READONLY_USERNAME`), the stub yields `undefined` there, so a guard comparing against it is **inert while every test passes**. Flag any diff that adds a barrel import to a file whose test stubs that barrel without adding the symbol to the stub in the same commit.
- **`mock.module("../client" | "server", …)` barrel mocks** — Bun's `mock.module` is process-global and hoists across the whole test run, so mocking a barrel in one file bleeds an unexpected stub into unrelated suites (the cause of the flaky auth-rate-limit test). New tests should NOT mock a barrel — mock the leaf `pg` dependency (FakePool) and run the real code, the `users.test.ts` pattern. Flag any new barrel mock.
- **Asymptotic cost — no N-round-trip loops** — if the diff has a `for` loop calling `pool.query` / `Table.method` / `await fetch` / `await imap.<cmd>` over a per-user or per-mailbox collection, flag HIGH. Single batched call (`= ANY($1::text[])`, `IN`, `unnest`, `WITH` CTE, `Promise.all` for genuinely-independent IO) is the default, not a perf-optimization. The reflex of "loop over ids and await each one" is a smell the maintainer pushes back on. The fix is to widen the Table method itself (per the no-bypass rule above), not bypass with raw SQL or a JS loop.
- **Full-fetch read endpoints scale with users** — flag any new `GET /<entities>` route that returns "all of X for the user" with no `?since=<cursor>` filter and no `?include-deleted=true` tombstone mode. Accept transitional "full-fetch + filed follow-up issue" but flag a NEW endpoint shipping without the pattern as a regression. Indexes for the `updated >= $cursor` access path must be in place.
- **Cron job hot-path multiplies by user count** — anything inside `for (userId of userIds)` in `idle-manager`, `scheduledSync`, the spam-score recompute, multiplies cost by user count. A per-user UPDATE that scans the user's table without an index, a per-user N-round-trip cascade, all flag at HIGH.
- **Barrel re-export collision shadows the intended function** — `lib/index.ts` does both `export * from "./postgres"` AND an explicit `export { foo } from "./mails"`. On a name collision the **explicit named re-export wins**, so `import { foo } from "server"` resolves to the `./mails` version even when `./postgres` has one too. This silently bit PR #619: `getDomainUidNext`/`getAccountUidNext` had a throwing repository impl in `postgres/repositories/mails.ts` AND a swallowing `catch → return 1` wrapper in `mails/search.ts`; every `from "server"` caller (send, IMAP APPEND/COPY/MOVE) got the swallowing wrapper, so the PR's "abort on reservation failure, never fabricate UID 1" invariant was true only for `receive.ts` (which imported the raw repo fn directly). When a PR changes a function's error/return behavior, **trace which copy the `"server"`/`"client"` barrel actually resolves for each caller** — grep for a same-named wrapper in a sibling module (`search.ts`, a `*.wrapper.ts`, etc.) and confirm the named re-export isn't shadowing the one the PR edited. A duplicate single-value wrapper that only adds a `catch`/`?? fallback` is itself a smell worth flagging.
- **PII in committed source comments AND commit messages — not just PR/issue text** — the PII gate is usually run on PR bodies, but real-account currency figures, institution names (`<institution>`…), and account labels (`<account label>`…) also leak via **code comments and the commit-message body**, which ship permanently in public source + git history. Flag HIGH any committed comment or commit-message body that cites a concrete `$NNN,NNN` figure, a real financial-institution name, or a real account label — verification narratives belong qualitative ("a spurious deficit reconciling to a surplus modulo manual appreciation"), never with the numbers.
- **A real mail address at the operator's own domain is PII, and E2E evidence is where it leaks** — measured 2026-09-18: 25 public artifacts in this repository carried a per-service alias roster (`<alias-1>@`, `<alias-2>@`, `<alias-3>@`, `<alias-4>@`, `<alias-5>@`, `<alias-6>@`, `<alias-7>@`, …) with per-alias mail counts beside it, harvested into PR bodies and issues as evidence against the real mailbox. Every one is a confirmed-deliverable address, and the **set** discloses which services the operator holds accounts with — so this is disclosure even where no single line looks sensitive. The gate had no rule for the operator's own domain until that day, so a diff or PR body can pass the PII gate on an old checkout and still leak. Flag HIGH a non-fixture local-part at the operator's mail domain, and any third party's address at a real external domain, wherever it appears — PR body, issue body, test fixture, committed comment, screenshot alt-text. Fixtures (`admin@`, `test@`, `bob@`, `ut-spam-*@`), bot identities and the published `CODE_OF_CONDUCT.md` contact are allowed; a service name as the local-part is exactly what is not. Scrub to `<alias-N>@<domain>`, stable across artifacts so cross-referencing prose stays coherent. Same reasoning as the currency rule above: the evidence must be qualitative ("the largest mailbox", "an alias with ~700 mails"), never the roster.
- **Prefer an in-house primitive over an external dependency** — when a diff adds an npm package (e.g. `idb`) for something small enough to hand-roll, flag it. In PR #618 an `idb`-based `idbStore.ts` was rewritten as the hand-rolled `QueryCacheStore`. A new external dep that duplicates an in-house primitive (cache accessor, Table layer, test harness) forks the mental model and adds supply-chain surface. Before approving any new `package.json` dependency, grep this repo for an existing hand-rolled equivalent. Genuine carve-out: a nontrivial thing the repo has not built (crypto, a parser spec).
- **Use existing named constants, not re-typed string/value literals** — when a diff hardcodes a literal that the codebase already exposes as a named constant (a kind/scope enum value, a default, a magic string), flag it. The maintainer, PR #619 (r3483232624): *"Why don't you use `${USER_ID}` and `${SENT}`?"* — the diff inlined raw values where `USER_ID` / `SENT` constants existed. Grep for an existing exported constant whose value matches any literal a diff introduces (especially in SQL templates and UID/flag/scope code) and prefer the named reference — it keeps the literal single-sourced and self-documenting.
- **Self-documenting code — flag redundant JSDoc, missing edge-case tests, loose runtime contracts** — every diff's docstrings, tests, and runtime validation must EARN their lines. Three smells:
  1. **JSDoc that restates the function name / signature / implementation.** *Smell:* `/** Checks whether the mail is unread. */ const isUnread = (m) => !m.read`. *Pass:* one-line intent + a load-bearing *why* (an upstream constraint, a hidden coupling, a past incident the implementation can't show). Bullet-doc that repeats what each predicate one-liner already shows adds lines and no information.
  2. **Tests skip edge cases the function NAME implies.** *Smell:* a function tested only on the happy path. *Pass:* tests every case the reader would infer from the name. Writing the cases the *name* promises (not just the cases the current implementation happens to handle) is what stops a future refactor from silently flipping the semantic. For IMAP op handlers in particular — `MOVE` implies destination-create-if-missing, source-unflag, EXPUNGE-style sequence-number handling, RFC 6851 COPYUID emission; every one should have a test, not just the happy path.
  3. **Runtime contract wider than the name implies.** *Smell:* `getActiveAccount(user_id)` whose return type is `Account | undefined` — the name says it exists, the type silently widens. *Pass:* rename (`findActiveAccount`) or throw on the contract violation at the boundary. IMAP parsers / route handlers parse external input to the expected shape and throw on mismatch.
  **Comment hygiene — self-documenting code is the north star. Flag every violation.** Never-in-code list: PR narrative / change history, `#N` / issue / PR refs in source, restated fixed bugs, hex ids or sentinel values from bug logs, attribution by name, comments that restate what a well-named identifier already says. Four narrow exceptions: (1) JSDoc on public/abstraction surfaces where an IDE tooltip earns the space, (2) `TODO` markers, (3) one-line WHY when the *why* isn't derivable from the code (a Postgres/Bun quirk, IMAP RFC nuance, race workaround), (4) long external context lives in `docs/*.md`. If a comment answers "would a fresh reader who never saw this PR still need this?" with NO, flag it.
- **Log persistence + runtime metrics belong at the infra layer, not the app** — for logging PRs, flag any change that tee's log lines to a file inside the app process or emits a per-N-second memory/CPU heartbeat into the log stream. The correct shapes (inbox #641, the maintainer 2026-07-01): capture logs via the container-runtime log driver (compose `logging: driver: journald`; journald owns rotation/TTL via `SystemMaxUse`/`MaxRetentionSec`), and read memory/CPU as METRICS from the cgroup via the Docker socket (`GET /containers/{name}/stats`) in a monitoring sidecar, never from the app. Keep genuine EVENTS (boot diagnostic, error traces) in stdout; keep METRICS in the metrics path. The maintainer: *"How does AWS or typical cloud providers do this? Do they hijack console.log?"* and *"Can we monitor the memory in docker layer? Logging this way seems anti pattern."*
- **File-split refactor must split its TEST file to match — flag a monolithic test alongside decomposed source.** When a PR splits one source file into per-component files (`X.ts` → `X/{a,b,c}.ts`), the test file must be partitioned the same way (`X/a.test.ts`, `X/b.test.ts`, …) in the SAME PR — each per-component source gets its matching per-component test. Flag any split-source PR whose test stayed one file. The maintainer, inbox #706 (2026-07-27): *"Why don't you split mails.test.ts?"* Two gotchas when the test moves INTO the new dir: `await import("./X")` → `await import(".")` (same-dir index), and source-scan guards' `path.join(import.meta.dir, "X")` → `import.meta.dir` with a `.test.ts` readdir filter so the test file isn't concatenated into the "source under test" string.
- **`process.exit()` preceded by a fire-and-forget async call (alarm, log-flush, webhook POST) silently drops that call.** `process.exit()` is synchronous and forcibly ends the event loop; a `fetch()` fired without `await`/race in the same tick has not sent its bytes yet. Flag any `log → sendAlarm(...).catch(() => undefined) → process.exit()` shape (crash handlers, fatal-startup handlers, any last-gasp reporting before exit) — the correct shape is `await Promise.race([sendAlarm(...).catch(() => undefined), timeout(N)])` before the exit, so a slow/dead webhook can't turn the fix into a new hang. inbox #735 shipped the fire-and-forget shape first; the reviewer caught it, reproduced the drop with a local webhook harness, and the fix landed as a bounded race in `src/server/lib/startup-failure.ts`. The exact same pre-existing race was found (unfixed, filed as inbox #736) in `start.ts`'s `uncaughtException` handler — grep any other `sendAlarm(...).catch(...)` immediately followed by `process.exit()` for the same bug.
- **A build-time-folded constant means the SOURCE and the SHIPPED ARTIFACT disagree — audit the bundle, and never trust `src/`-only grep or a green test.** Bun's bundler constant-folds the exact member expression `process.env.NODE_ENV` into a literal at build time. `Dockerfile` builds with it unset and `pack.ts` bundles `node_modules` with no `external`, so **every** such read — app code and vendored dependency alike — shipped as `false`/`"development"`, and no container env could revive it. inbox #766 was filed against one symptom (logger never emitted JSON); the same fold had silently killed **six** production branches, four security-relevant: no `trust proxy`, no HSTS, session cookie without `Secure`, raw internal error strings in 500 bodies, and — invisible to any `src/` grep — express's own `env` frozen to `"development"`, which made finalhandler return the full `SyntaxError` stack with absolute server paths for an **unauthenticated** malformed-JSON body. Four sub-rules: (a) only the exact dot member expression folds — `process.env["NODE_ENV"]`, destructuring, and aliasing all survive, so the fix is one bracket-access helper every call site routes through, not a build flag (`Bun.build({ env: "disable" })` does NOT suppress it); (b) for anything build-time-sensitive, verify by **running the built artifact**, because `route.test.ts` already had a green `hides error message in production` test the entire time prod shipped the opposite — a test that exercises source certifies nothing about the bundle; (c) a guard on the helper module alone is insufficient — require a source scan asserting the folded expression appears nowhere else under `src/server`, which is the only check that would have caught all six (note it matches source text, so comments spelling the expression trip it — reword the comment rather than teaching the scan to strip them); (d) newly *activating* a long-dead production branch has deploy risk worth flagging — restoring `cookie.secure` + `trust proxy` fails **quietly** if the reverse proxy doesn't forward `X-Forwarded-Proto`, because the session store restores `secure` from the row and `rolling: true` re-issues it, so existing sessions survive and only new logins silently fail. Fixed in inbox #789.
- **Axis / sentinel / normalization at a helper boundary → audit EVERY sibling in the same file for the same gap, and every downstream consumer for a "made-reachable" bug.** When a PR adds a discriminator flag to a helper (`isUidCommand: boolean`, `isOwner`, `isAdmin`, `isDraft` — any "which of two axes are we on") or tightens sentinel/reversal normalization on one range-shaped input, do NOT stop at the touched helper. Grep the same file for every function that takes the same value-type (`SequenceSet`, `Range`, `Set<id>`, any `{start, end}` pair) and check each for the SAME class of gap in the SAME PR. And after every fix commit, ask *what previously-silent code path does this fix newly unmask?* — fixing an upstream counter/predicate that used to skip the cap gate now fires the cap gate, which puts control into a downstream branch that may still carry the pre-fix shape (a silent bypass becomes a silent zero-fetch). inbox #793 took SIX review rounds to close one class: R1 HIGH clamp-UID axis-mixing → R2 MED clamp-UID enclosure over-fetch → R4 MED counter-UID cap-bypass → R5 HIGH clamp-UID missing `*`/reversal + R5 MED counter-SEQ missing `*`/reversal → R6 MED clamp-SEQ (made reachable by R5's counter-SEQ fix). Every one was in the same file, and every one shipped only after the finder enumerated ALL sibling helpers and their normalization matrix.
- **Dead definitions orphaned by the diff's own migration.** When a PR supersedes a route/helper/endpoint (singular → plural, N calls → one batched call, old shape → new shape), grep for remaining in-tree callers of the superseded one. **Zero callers means it must be deleted in the SAME PR** — a route that looks supported and has no caller is worse than either state. Then grep the deleted file's basename repo-wide: JSDoc, test-file headers, and mid-file comments that name it survive the deletion and go stale.

- **A name states the component's FUNCTION or ROLE — flag any identifier whose distinguishing word describes the interface shape instead.** The test is **"could I delete this word and lose nothing?"** — every networked component has an API, so `-api` carves out nothing. Words that usually fail the test: `api`, `service`, `manager`, `handler`, `util`, `data`, `core`, `common`, `helper`, `wrapper`. Words that pass name a domain noun or the verb the component performs. Apply to modules, route groups, tables, classes and files, not just top-level names; flag it as a MED when a diff introduces such an identifier and a descriptive alternative is obvious from the body. Between two already-descriptive names, prefer the **more precise** one ("ML" over "AI", because "AI" is a superset that would also cover rule-based systems) — when the maintainer asks "which is better, X or Y," they are asking which is more precise, not which reads better. Sits with the runtime-contract-wider-than-the-name rule above.
- **This repo is PUBLIC — committed prose must not name the maintainer as a person or cross-reference other projects.** Flag any `.md`, JSDoc, or doc-comment line in a diff that says the maintainer's name, "per <name>", or justifies a choice by pointing at another project ("same stack as <project>"). The user story is fine — write it as "the user." **The discriminator is prose vs. identifier:** a URL or `owner/repo` slug a contributor actually needs (`git clone https://github.com/<owner>/<repo>.git`, "open a PR against `<owner>/<repo>`", a demo link, a contact address) is allowed; a sentence that names other projects, or that leaks the existence of the maintainer's other work, is not. This is the docs-and-PR-body sibling of the comment-hygiene attribution ban and of the PII-in-comments rule above — same never-in-public surface, different content class.
- **Reject a root-cause claim in a PR body that doesn't explain the error's SHAPE.** "floating-point precision" and "rounding" are zero-mean and non-accumulating; if the reported symptom is *directional* or *grows with window width / row count*, those causes are falsified by the symptom itself and the PR is built on a wrong diagnosis. Require the body to state what the mechanism predicts about sign and scaling, and to match that against the observed shape.
- **An alarm-suppression branch is reviewed on THREE axes — who PRODUCED the error, what else the `return` skips, and whether the match is keyed on the condition or on one producer's vocabulary.** Flag any diff that adds or extends a message/substring filter at an alarm-reporting boundary (a `sendAlarm` call site, `POST /api/client-error`, an `error` / `tlsClientError` handler on a listener). **(a) Producer.** An error emitted by *our own code or our own users* must page — The maintainer closed inbox PR 651 with *"Close this. I want the error to page"* (2026-07-07), and issue 629 two seconds later with no comment of its own — the quote is on the PR, not the issue. An error emitted by an *anonymous third party* against an internet-facing port is not ours and may be suppressed — The maintainer themselves merged inbox 393 (2026-03-28) to silence bare TCP probes on 465. **The discriminator is who produced the error, not whether the code is an alarm boundary**; a rule that stops at "it's a denylist" both blocks the legitimate case and gets ignored when it does. **(b) What the `return` skips.** `if (benign) return;` placed ABOVE `logger.error` suppresses the *evidence*, not just the page: a real failure hiding in that bucket leaves no server-side trace at all, so the next investigation greps the logs and finds nothing. inbox's `src/server/lib/smtp.ts` shipped exactly that shape for **twelve** allowlist entries until 1024 split it into `logger.warn(...)` then `return`, skipping only `sendAlarm`. MED, and the assertion must count the warns (`warnings.filter(...).length === N`), not merely check `error` was not called. **(c) Key.** A substring match is keyed on the *producer's vocabulary*, so the same condition reached through a second code path re-alarms and the list still reads complete. `smtp.ts`'s entries matched OpenSSL negotiation function names plus `smtp-server` strings — the vocabulary of the STARTTLS *upgrade* path — while port 465's implicit-TLS path (`secure: true`) raises Node's own generic `TLS handshake timeout` for the identical client behaviour (connects, never completes the handshake), so it fired 21 h 09 m 52 s after the list was last certified and pre-empted a whole alarm-triage session. Ask which code paths can raise this condition and require the enumeration, not the author's confidence — the sibling-helper audit applied to an allowlist instead of a helper signature.
- **A credential change must evict every surface that authenticated against that credential — flag a rotation/reset/revoke path that only clears HTTP sessions.** inbox authenticates on three surfaces and **two of them derive the grant once per connection and never re-consult the stored hash**: the HTTP session row, the IMAP authenticated session, and the SMTP submission connection. So an eviction that deletes session rows leaves a mail client holding unrestricted `FETCH`/`STORE`/`APPEND`/`MOVE`/`EXPUNGE` and submission for the life of its socket — the longest-lived grant survives the control whose whole purpose is revoking it, and the repo ships an autoconfig document for clients whose connections are long-lived by design. Correct shape (PR 1010, 2026-10-01): a per-surface registry of live authenticated connections (`imap/session-registry.ts`, `smtp-registry.ts`) that the credential writer sweeps, each keyed on **the credential the connection presented** rather than the effective user, so a read-only `session_authenticated_as` connection survives a password change it does not depend on. HTTP, IMAP and SMTP all initialize in one process (`start.ts`), so no cross-process signalling is needed — a design that moved them apart would need it, and that is the thing to ask about, not whether the sweep exists. This is the sibling-helper audit applied to the authentication axis: the question is never "did you delete the sessions", it is "enumerate what holds a grant derived from this secret." MED normally, HIGH when the path is a user-facing security control (password reset, "sign out everywhere", account disable).
- **In a handler that both revokes and rewrites a credential, flag the ordering and flag expensive derivation sitting inside the revoke window.** Two separate properties, both invisible in a passing test. **(a) Revoke BEFORE the write.** A fault then aborts with the old credential and its reset token intact — a retryable reset — whereas write-then-revoke on a fault leaves a *new* password whose old sessions survived, which is the original defect with a narrower trigger. **(b) Compute the hash before the DELETE.** A bcrypt round between the revoke and the write puts measurable latency inside the one interval where the old credential is still live and its sessions are already gone. **(c) The eviction helper propagates rather than resolving to 0** — a caller that cannot distinguish a failed DELETE from "no sessions to delete" reports the rotation complete while the grants it was meant to revoke are still live (`deleteSession`'s existing contract is the precedent). PR 1010. Flag any revoke-and-rewrite sequence whose order is write-first, and any hash/KDF/network call between the two.
- **An identity used as a rate-limit, quota, lockout or audit key must not be settable by the caller — and a hop-count / boolean proxy-trust setting does NOT make it unsettable.** Trace the key to its source in one hop and ask *who can set this?* Flag any `getClientIp`-shaped helper that reads `X-Real-IP` or `X-Forwarded-For` **before** the socket-resolved address: those headers are supplied by whoever sends the request, so the caller picks its own bucket and a per-request rotation turns an N-attempt cap into an unbounded one. inbox 1023 measured it on the live login route — fixed header value: 5 allowed / 3 rejected; rotating value: **0 of 8 rejected**, on both header names. **The one-line fix is insufficient and that is the part to flag**, because it looks complete: reverting only the proxy-trust half of 1023 while keeping `req.ip` still failed 2 tests including the bypass case, since a hop count (`trust proxy = 1`) trusts whichever peer opened the connection — so a request reaching the app port without passing the proxy still names its own `req.ip`. The peer gate must be an **address predicate** (`["loopback", "uniquelocal"]`), and even then it is not airtight: `proxy-addr` trusts all of `10/8`, `172.16/12`, `192.168/16`, `fc00::/7`, so a second container on the compose bridge or a host process hitting the published port still spoofs — that residual belongs in `docs/` as an operator contract, flagged if the PR claims more. Three collateral checks: (a) a docstring asserting a header *"cannot be spoofed by the client"* is a deployment assumption, not a guarantee — flag it as prose that cannot be verified from inside the tree; (b) **changing proxy trust has a blast radius beyond the bucket** — the same setting governs `req.secure`, which `express-session` consults before setting a `Secure` cookie, so a wrong value is a **silent auth outage** (no `Set-Cookie`, nobody stays logged in), not a degradation, and the PR must pin it behaviourally rather than argue it; (c) each distinct rotated key also retains a limiter `Map` entry until the sweep, so the rotation is unbounded memory too. Repo note: `src/server/lib/http/` is the fixed site (1023, merged 2026-10-02); `app.test.ts` asserts the `trust proxy` value exactly, so flag any diff that returns it to a hop count.
- **An absent / error / empty response is not a product state — flag any diff that maps one to a fact about the system without a control target.** `404` ⇒ the feature is off, `0 rows` ⇒ it never happened, an omitted JSON key ⇒ disabled, a non-zero exit ⇒ the thing under test is broken: each has at least one other cause (no permission, wrong scope, admin-only field, wrong route) and the response cannot tell them apart. The check is one call: **run the identical request against a target whose answer you already know in the OTHER direction**, and if both answer the same, the response is not measuring the claim. For example, GitHub's secret-scanning alerts endpoint returns `404` for `cli/cli`, `github/docs` and `octocat/Hello-World` alike, because it needs administrator access that no OAuth scope confers, so `404` reports the caller's access and never the setting. Require **three** verdicts where a diff offers two — *in force* / *drifted* / *not readable with this token* — and flag the collapse of the third into either of the first two. Two corollaries: a **fixture must emit a status the live API actually returns** (a fixture manufacturing a `403` the endpoint never emits validates a mapping the API contradicts), and an **unknown verdict belongs in the report, not in the exit code**, unless the PR shows the success exit is still reachable — a reserved "unknown" exit can hold forever and make its downstream consumer dead code.
