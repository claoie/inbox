# §F.imap — IMAP protocol / session / wire

Load when the diff touches `src/server/lib/imap/**`, `src/server/lib/smtp.ts`, `src/server/lib/mails/**` (send/receive), or any code that reads/writes the IMAP/SMTP wire.

- **A protocol upgrade in place (STARTTLS and anything shaped like it) has a three-step order, and each step is a separate bug** — (1) detach the cleartext reader from the raw socket *before* wrapping, because `TLSSocket` reads through the same handle and a live `data` listener eats the ClientHello; (2) write the tagged/positive response in **cleartext and before the wrap** (RFC 3501 §6.2.1 / RFC 2595 §3: negotiation begins immediately after its CRLF — a conformant client holds its ClientHello until it reads that line, so wrapping-then-answering deadlocks, and the answer would go out encrypted to a peer not yet in TLS); (3) only then wrap and re-attach, and **flip the "am I secure now" flag** or the post-upgrade capability list still advertises the upgrade. Flag any `new TLSSocket(existing, { isServer: true })` that awaits `secure` before answering. Note the failure mode is a **hang, not an error** — no log line, no exception, just a client that never gets a response — so it survives every green test suite and only a live client drive finds it. inbox #838, 2026-08-15.
- **A sanitizer/encoder PR must sweep the READ sites too, not just the write sites** — when a diff hardens "attacker-controlled stored value → emitted string", the natural sweep is every *interpolation* of that value. The sibling class that gets missed is every place the code **matches or parses its own emitted output**, because a stored value that lands earlier in the block can win the match. inbox #828 (2026-08-13) shipped a first cut that removed a `boundary="([^"]+)"` recovery regex over the header block but left `rewriteContentType`'s unanchored `/Content-Type: [^\r\n]+/` right beside it — `Subject` is emitted ahead of `Content-Type`, so a stored subject containing the literal text `Content-Type: ` was rewritten instead, **with no CRLF required**, and `BODY[]` disagreed with `BODY[HEADER]` about the user's subject. Flag: any `.match(` / `.replace(` / `.split(` / `indexOf` over a string the same function just built from user data, and any such regex that is unanchored when it should be `^…/m`. Ask "which fields are emitted BEFORE the one this pattern targets?"
- **A byte-count-changing serializer invalidates persisted size columns** — `mails.rfc822_size` is stamped at INSERT (`repositories/mails/core.ts`) and returned verbatim on a cache hit, so any diff that changes how many bytes the header block or MIME framing emits silently breaks the `RFC822.SIZE == BODY[] octets` invariant for **pre-deploy rows**. Green tests prove nothing here — they build and measure from the same code. Flag any sanitizer/encoder/framing change that alters emitted length and require either a NULL-the-stale-rows backfill (tracked, as a one-off recovery script — not hot-path cleanup code) or an argument for why length is preserved. "Character-for-character substitution" preserves **code units**, not bytes; `segmentByteLength` measures bytes.
- **A wire length is OCTETS; a JS string index is UTF-16 code units** — flag HIGH any `substring`/`slice` on a **string** whose bound is an integer parsed from network input (IMAP `{N}` literals, MIME part sizes, `Content-Length`), and any `buffer += data.toString()` inside a `socket.on("data")` handler. The first takes too few characters for a multi-byte payload; the second decodes each TCP segment independently so a UTF-8 sequence split across a segment boundary is U+FFFD before any parser runs. Both are invisible to ASCII-only fixtures, which is every fixture written in English — so **require a test with a multi-byte payload AND one split mid-sequence across two `data` events**, and treat "tests pass" as no evidence. Correct shape (PR 836, issue #805): accumulate in a `Buffer`, split lines and slice payloads as byte operations, decode each piece once whole, and pass the decoded payload **out of band** (`ParseContext.literals`) rather than embedding it in the command text and re-deriving an offset — an offset that must hold both units at once is a latent bug, a queue cannot disagree with itself. Watch for the second-order form too: a short slice that leaves a stray `\n` in the buffer turns silent corruption into a **wedged session** (no tagged completion until the socket timeout), which is strictly worse. Same review found the identical bug pre-existing in `parseAppend`'s inline extraction — when you find one, grep every sibling literal/length reader (the sibling-helper audit, §F cross-cutting).
- **IMAP idle-loop + bounded buffers** — watch the IMAP IDLE reconnect / setInterval drift / per-mailbox concurrency rules. inbox mail-fetcher changes are high-blast-radius.
- **Envelope-vs-header dual filtering** — inbox supports both `envelope_to` (SMTP-time) and `to_address` (header-time) for listserv-routed mail. Removing one or unifying them silently is a real regression. Flag any diff that narrows that surface.
- **IMAP per-connection hot paths** — the per-session command loop and the per-mailbox sync orchestrator are hot paths. A `for (mail of mails) await store.setFlags(...)` pattern inside FETCH/STORE/SEARCH multiplies by mailbox size. Batched UPDATE-with-IN is the default; flag the loop shape.
- **A per-session command stream must be SERIALIZED — flag any `async` socket/stream event handler that mutates shared state across an `await`.** `socket.on("data", async …)` is the canonical trap (inbox `handler.ts:119`, fixed in PR 808): Node emits `data` synchronously per TCP segment and does NOT await the handler, so each segment starts its own concurrent processing loop while they all share one `buffer`. Pipelined commands from a single client then execute concurrently. The visible damage is protocol corruption, not just a race — `writeFetchResponse` (`fetch-helpers.ts`) emits the `* n FETCH (…) {N}\r\n` literal header, `await`s a chunked body write, then emits `)`; any yield inside that sequence lets a concurrent handler's synchronous `write()` splice another command's output into the middle of the literal, and the client's parser desynchronizes. Flag HIGH. Correct shape: a per-connection promise chain / mutex so commands from one session run strictly in order. Note this is orthogonal to per-connection *concurrency caps* (a memory bound) — serialization is a correctness requirement.
- **Size-gated symptoms point at volume-dependent paths, and there is often MORE THAN ONE bug in that class.** When an issue or PR describes a defect scoped by size or volume — "INBOX only, smaller mailboxes are fine", "only large messages", "only after N items" — do not stop at the first plausible cause. Audit every path that behaves differently at scale: BODYSTRUCTURE/planning branches the client only takes for large bodies, `await` points that only yield under real backpressure, chunked/streamed writes, offset math, pagination. inbox 806 and 808 were two unrelated defects (RFC 3501 §9 quoting vs. per-session interleaving) inside the same "only the big mailbox" report on 2026-08-08, 75 minutes apart.
- **An OOM / resource-exhaustion under legal client load is a SERVER bug — bound the server's own resource use; do NOT propose banning/rate-limiting the client as the fix.** Flag HIGH any fetch/serialization/response path that materializes a per-caller copy of an unbounded body (multi-MB IMAP `BODY` FETCH, large query result), and flag any "ban/throttle the noisy IP" proposed as the PRIMARY fix for a server memory/CPU/pool incident. IMAP (and any protocol without a rate-limit contract) imposes no throttle contract — a server that OOMs under protocol-legal concurrent FETCHes is the defect. Correct fixes (inbox #713, the maintainer 2026-07-28 *"Do not ban that IP. It's a legit iphone that I'm using. Afaik there's no rate limit in IMAP contract."*): coalesce identical in-flight builds through the singleflight primitive and return a shared **Buffer** (not string — lets V8 GC the encode source and skips per-write UTF-8 conversion) so heap is O(distinct-in-flight-bodies); chunked backpressure-aware writes (64 KiB slices awaiting `drain`); per-connection concurrency caps at the handler.
- **The mail queries are a coupled group — a change to the address-filter or predicate shape of ONE must sweep the siblings in the same PR.** `getAccountStats` (account-row counts), `getMailHeaders` (per-account list render), `getUnreadNotifications` (badge), and `searchMail` all filter on the same address columns (`to_address` / `cc_address` / `bcc_address` / `envelope_to`). A change landing in one but not its click-through sibling ships a half-fix the user hits on first click: PR 525 added `envelope_to` to `getAccountStats`, surfacing a new account row whose list was empty because `getMailHeaders` still filtered on to/cc/bcc only (the maintainer, 12 min after merge: *"It seems the girhub emails are not included in mail list"* → companion PR 526). Grep the module for every function filtering on those columns; each either gets the same change or an explicit out-of-scope note in the PR body. And any E2E claim about a newly-surfaced entity (account row, badge count, search hit) must click INTO it, not just observe it appear. Same discipline as the sibling-helper audit (§F cross-cutting), applied to the query trio that shares one WHERE shape.

- **A per-dispatch rate budget is jumpable by one command that buys N units of work — charge the units, not the command.** Flag any throttle / quota / semaphore on a protocol handler whose accounting happens once per accepted command while a single command can draw N continuations, allocate N buffers, or re-enter the parser N times. inbox #944 (issue #861, merged 2026-09-16): the drain loop charged its per-second budget at dispatch, and one command could chain up to `MAX_LITERALS_PER_COMMAND` (64) literal declarations — 64 continuations drawn, 64 payloads moved through the buffer, 64 parser re-entries, all free against a budget the same octets pay in full when they arrive as commands of their own. Note that a **cap is not a rate**: PR #843 had already bounded the chain at 64, which bounds the total while leaving the rate uncharged, so "a sibling PR capped it" is not a reason to close the finding. Ask of every budget: *what is the largest amount of work one accepted unit can buy?* Second half of the same review: a `socket.on("data")` handler that rebuilds the whole session buffer per TCP segment is O(n²) in segments and is the memory-floor mechanism, not a cleanup — hold the buffer linearly (append + consume offset), and see the OCTETS-vs-UTF-16 rule above for the decode half. When a PR bundles a residual defect with a live one, require the body to label which is which, or review effort lands on the cheap half. Pairs with the standing rule that an OOM under protocol-legal load is a SERVER bug — bound the server's own work, never propose throttling the client as the primary fix.
