# §F.postgres — Postgres / Table / migrations

Load when the diff touches `src/server/lib/postgres/**` (models, repositories, database.ts) or any migration/DDL surface.

- **A `Table`-written table whose DDL lacks a column the shared builder hardcodes** — `buildInsert`/`buildUpsert` (`postgres/database.ts`) stamp `updated = CURRENT_TIMESTAMP` on every generated INSERT, and `Table.insert`/`Table.upsert` now gate that on `"updated" in this.schema` (PR #734, issue #687). Before that gate, `mailboxes` — the one builder-written table declaring only `created` — made **every IMAP `CREATE` fail** with `column "updated" of relation "mailboxes" does not exist` → `NO CREATE failed`. Flag: (a) any new `createTable` whose schema omits `updated` *without* verifying the gate still covers its write path; (b) any diff re-hardcoding `["updated"]` in the builders or dropping the `stampUpdated` option; (c) removal of the consistency sweep in `postgres/database.test.ts`, which walks the exported `tables` registry from `initialize.ts` and asserts the builders can only emit columns the table's own DDL declares. Note the class of bug is **invisible to unit tests that mock the pg pool** (the FakePool pattern) — generated SQL never meets a real schema — so "tests pass" is not evidence here; ask for a live round-trip or the registry sweep.
- **Live binding vs eager capture** — when source modules eagerly construct objects from imports (`const pool = new Pool()`), later `mock.module("pg", …)` does NOT retroactively rebind. The pg-FakePool seam (mock `pg` BEFORE the lazy pool is first constructed, as `users.test.ts` does) is the correct workaround. Flag a new test that `mock.module`s the `server`/`client` barrel — that bleeds process-globally across files; mock the leaf `pg` dependency instead.
- **SQL parameter ordering** — when adding/removing a column from an INSERT/UPDATE, every `$N` placeholder downstream shifts. Walk the parameterized values to be sure.
- **Extend `Table.query`, don't bypass it** — when a repo function needs a query shape the existing Table method doesn't expose (date range, custom `orderBy`, `excludeDeleted` override, `IN (...)` predicate, etc.), WIDEN the Table method's options arg rather than reaching for `buildSelectWithFilters` + `pool.query` directly in the repo layer. Flag any diff that calls `buildSelectWithFilters` / `buildInsert` / `buildUpdate` / `buildUpsert` / `buildSoftDelete` from a repo when a Table wrapper is one options-arg-widening away. inbox's own `Table.updateWhere` `{op:'IN', value:[]}` extension (PR #472) is the precedent for doing it right. Genuine carve-outs (custom aggregates, full-text) are fine but want an explicit comment. Copying an existing bypass is NOT a justification — it spreads the anti-pattern. Recurs hard: the maintainer, PR #522, *"I always tell you to prefer to extend the table methods… and you always choose the other way."*
- **Indexes match access patterns** — when a diff adds a query that filters by a column, check `models/<table>.ts` for an index on that column. If the table grows linearly with users (`mails`, `mailboxes`, `spam_allowlists`, `users`, etc.) and the filter column isn't indexed, the index lands in the same PR.
- **Constraint-adding migration needs an orphan/violation check first + a not-already-present check** — when a PR adds an FK / UNIQUE / CHECK / NOT NULL enforced at migration time (these auto-run on deploy), flag MED unless the PR body shows: (a) the constraint isn't already declared on the model / present in `pg_constraint`, and (b) a prod-clone violation count of 0 — a single violating row aborts the whole deploy and rolls it back. An FK enforces row EXISTENCE only; it does NOT cover soft-deleted rows, so an app-layer existence check is still required where a soft-delete race matters.
- **`Table` filter builders DROP an undefined filter, so a missing id silently widens a mutation from one row to every row the remaining predicate matches.** Flag HIGH any `updateWhere`/`deleteWhere`/`queryOne` call whose filter object mixes a scoping column (`user_id`) with an id that can arrive undefined from an unvalidated `req.body` field. `buildSelectWithFilters` does `if (isUndefined(value)) continue;` and `updateWhere`/`deleteWhere` filter undefined entries out, then only refuse when the list is **completely** empty — `user_id` alone satisfies that guard. inbox #790: `POST /api/mails/mark` with body `{"read": true}` and no `mail_id` passes the ownership guard (`queryOne` returns an arbitrary row of the caller's) and then emits `UPDATE mails SET read = $1 WHERE user_id = $2` — the entire mailbox, silently and irreversibly. Note the inversion this creates: the raw-SQL sibling `markMailSpam` is **immune** precisely because it bypasses the builder and writes a literal `mail_id = $2`, which binds NULL and matches nothing. So the framework method is more dangerous than the query it was meant to replace — do not treat "uses `Table`" as evidence of safety, and require boundary validation of every body-sourced id before it reaches a repository call.
- **Binary in a JSONB column round-trips as an integer map — attachments are the live case, and any UUID-reference redesign inherits the orphan-reclamation bug.** `mails.attachments` is declared `JSONB` (`src/server/lib/postgres/models/mail.ts:113`, typed `object | null` at :74/:170), so a `Buffer`/`Uint8Array` serialized into it comes back as `{"0":137,"1":80,…}` — one JSON number per byte, several times the size of the bytes themselves, read in full by any `SELECT` that touches the row. This compounds open issue **787** (`searchMails SELECT *` reads up to 30 MB of mail bodies per query to return 212 kB of headers): blob-in-row is exactly what makes a wide `SELECT` catastrophic. Flag any diff that (a) writes new binary into a JSONB/`object` column, or (b) `SELECT *`s a table with a blob column on a list/search path — column-project instead. **The maintainer has an open, unanswered design question here** (2026-08-09): *"Tell me how to fix the attachment. Can I save the integer array as file and store UUID in DB?"* If a PR implements that shape, the review MUST check for a reclamation path — open issue **811** records that attachment files are *already* never reclaimed (orphaned on every mail delete, and on ingest for every multi-recipient mail), so a UUID-reference design without deletion + multi-recipient refcounting just re-files 811 at larger scale.
- **A jsonb write rewrites the WHOLE document — flag any partial-update path that isn't read-modify-write, and require a sibling-fields-survive test.** Every UPDATE to a jsonb column (`mails.attachments` and the other `object`-typed columns are the live case) replaces the entire document; code that "writes the field it cares about" silently clobbers the siblings. Trace the write end-to-end, confirm it merges into the current document, and require a unit test that updates one field and asserts every other field unchanged. See the binary-in-JSONB bullet above for the size half of the same hazard.
- **One-time legacy-state cleanup never ships in a production code path — flag any `DO $$` fixup block in `initialize.ts`, any self-healing scrub added to an engine/sync/startup step, and any data-repair script bundled into a behavioral PR.** The smell test: after the cleanup clears its N legacy rows, will any NEW row ever match its WHERE clause? No → it's a one-off the maintainer runs manually; it does not get committed to a path that runs forever (the maintainer, inbox 486: *"Don't permanently insert a one-off backfill code. I'll run this backfill manually"*). Yes — the condition is ongoing (e.g. rows newly soft-deleted every sync) → inline is fine. A repair script inside a fix PR is additionally suspect because the damaged state may already be repaired — *"Remove the fix script from 715. I already handled that"* — the PR body must state the assumption so the maintainer can say "already done" before review, and the repair ships as its own artifact, never as a file in the behavioral diff.
- **Every read derives its row set from the session user and every write proves ownership of caller-supplied ids — flag HIGH any route/repo path where a body-sourced id reaches a write, or a table-wide read ships rows, without `user_id = $session` or an ownership join.** A route whose update branch looks safe can have a create branch that mints rows from a caller-supplied parent id with no ownership check — a CRITICAL cross-tenant IDOR — so check every branch, not the one everyone cites. Ask of every touched read: where is the user scope? Of every write: can the id in this request belong to another user, and which statement refuses it? "The FE only sends its own ids" is never an answer; "returns everything and the FE filters" fails on both axes (wire cost + exposure).

- **An upsert on a "make sure this exists" path must not carry a USER-MUTABLE column onto its `ON CONFLICT` clause — it silently reverts the user on every run, and the fallback literal is what ships.** `buildUpsert` (`postgres/database.ts`) emits `ON CONFLICT (pk) DO UPDATE SET …` for every column the INSERT wrote, so a seed/ensure/initialize function that always supplies a value re-asserts it at every boot. inbox #961 (issue #907, merged 2026-09-16): `initializeAdminUser()` upserted `password: ADMIN_PASSWORD || "inbox"` onto the row it had just read, so (a) a password set through the real reset route `POST /api/users/set-info` reverted at the next restart with no signal, and (b) with `ADMIN_PASSWORD` unset the value re-asserted every boot was the literal `inbox` published in `.env.example`. Flag any upsert inside an `initialize*` / `seed*` / `ensure*` function whose value expression is `ENV || "literal"` — the literal is a production credential path, not a dev default. Correct shape: supply the column **only when creating**, by passing `undefined` so it leaves the statement entirely (do not guard with an `if` at the call site — the column must not reach the builder); if removing the rewrite removes a real capability, bring it back as an explicit opt-in env (`ADMIN_PASSWORD_RESET=1`) that warns it re-applies until removed, and refuse the reset when the source value is empty rather than installing the published default. Require: the decision extracted as a pure function tested as a decision table, an assertion on the payload handed to the repository (not an intermediate), a mutation check naming which cases go red, and every doc stating the old invariant moved in the same commit. Ask of each column in the seed: *can a user change this after first run?* — if yes it is INSERT-only.
